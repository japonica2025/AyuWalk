# 织步记 MVP 设计规格

日期：2026-05-31
状态：供用户 review 的草稿
英文名：Ayu Walk。

## 产品定位

织步记是一款 iOS 旅行规划与电子手帐 App。产品有两个同等重要的核心能力：

1. AI 辅助旅行规划。
2. 电子旅行手帐生成与导出。

MVP 的目标是帮助用户把分散的旅行想法、截图、笔记和预订信息整理成可执行的旅行计划，再把这些结构化行程转换成简单但完整、可分享、可导出的电子手帐。

产品不应该从一开始就做成普通笔记 App 或纯手帐拼贴 App。它最强的差异化是：从规划数据到可执行行程，再到可分享手帐的完整闭环。

## MVP 范围

MVP 覆盖出行前规划和轻量电子手帐创建。

包含：

- 创建旅行计划。
- 根据手动输入，用 AI 生成初版行程。
- 导入截图和粘贴文本作为规划资料。
- 使用 MapKit 在地图上显示行程地点。
- 通过地图和每日时间轴编辑行程。
- 规划预算分类和预计花费。
- 使用 AA 计算器记录和拆分费用。
- 生成并编辑行李清单。
- 根据旅行数据生成电子手帐。
- 支持手帐页面的模块化轻编辑。
- 支持轻量贴纸系统。
- 导出可分享长图、PDF 和 Markdown。
- App 本地优先，后续预留 iCloud 和账号同步。

MVP 暂不包含：

- 完全自由画布式手帐编辑器。
- 大型模板市场。
- 多人实时协作。
- 完整自建账号系统。
- 公开社区信息流。
- 深度自定义地图底图风格。
- 自动解析小红书等受限社交平台链接。
- 完整餐厅和酒店推荐引擎。
- 实时营业时间优化。

## 产品流程

### 1. 创建旅行

用户可以通过两种方式创建旅行。

手动输入 + AI 辅助：

- 目的地。
- 旅行时长，可以按天数，也可以输入具体日期。
- 旅行目的，例如演唱会、蜜月、亲子游、好友出行、City Walk、购物、美食等。
- 预算偏好。
- 节奏偏好。
- 已有想法、必去地点或粗略笔记。

如果用户提供具体日期，AI 规划层后续应能在数据源可用时考虑节假日、工作日/周末差异和营业时间约束。

导入资料：

- 截图导入，包括旅行攻略、机票、酒店、聊天截图或预订截图。
- 文本导入，包括复制的攻略、备忘录内容、聊天内容或已有行程草稿。
- 导入资料也需要 AI 辅助：AI 应识别地点、日期、时间、票务、酒店、备注和不确定内容，并整理成可编辑的行程草稿。

链接导入后置，因为部分内容平台访问不稳定，可能存在登录限制或反爬限制。

### 2. 生成初版行程

AI 服务会把用户输入和导入资料转换成结构化旅行草稿。

生成结果应包含：

- 旅行摘要。
- 每日计划。
- 活动。
- 地点。
- 建议时间段。
- 备注和假设。
- 缺失信息提示。
- 对不确定识别内容的置信度或警告标记。

AI 输出必须是结构化数据，不能只是自然语言段落。App 会用这些结构化数据渲染地图、时间轴、预算、行李清单和手帐。

### 3. 编辑行程

规划工作台有两个联动区域：

- MapKit 地图，显示地点和路线预览。
- 地图下方或旁边的每日时间轴。

MVP 行为：

- 在地图上显示所有活动地点。
- 在地图上显示行程连线，让用户直观看到路线顺序。
- 使用 1、2、3、4、5 这类编号标注地点顺序。
- 允许用户以轻量方式拖动或调整地点顺序。
- 允许用户在时间轴中编辑活动。
- 让 AI 辅助重排、检测时间冲突、提升路线效率，并提示缺失的用餐或休息空档。

长期预留：

- 地图、时间轴、路线、交通、餐厅、酒店、预算、营业时间全部实时联动优化。
- 如果 MapKit 对地图底图风格限制过大，后续评估其他地图服务。

## 电子手帐

电子手帐是核心功能，不是附属功能。MVP 可以保持编辑简单，但功能链路必须完整。

手帐创建：

- 从旅行数据一键生成。
- 手帐 UI 应支持翻页效果，模拟真实书、手帐或日记本的阅读体验。
- 手帐以每日页面为主要组织方式，用户可以按天翻阅。
- 封面页。
- 旅行总览页。
- 每日页面。
- 可选预算和行李清单总结页。

页面内容：

- 标题。
- 日期和地点。
- 地图快照或路线摘要。
- 每日时间轴。
- 文字记录。
- 照片模块。
- 心情标签。
- 地点亮点。
- 必要时显示预算摘要。
- 必要时显示行李或清单摘要。

编辑模式：

- 自动排版优先。
- 模块化轻编辑。
- 用户可以调整手帐模块顺序。
- 用户可以为每个行程选择需要展示的模块。
- 默认勾选模块：标题、日期地点、照片模块、文字记录。
- 其他模块默认可选，例如地图快照、路线摘要、时间轴、地点亮点、预算摘要、行李清单摘要、心情标签和贴纸。
- 用户可以编辑标题、文字、备注、照片和心情标签。
- 用户可以选择少量模板或主题。
- MVP 不允许用户自由编辑所有字体、间距、图层或布局属性。

贴纸系统：

- 内置贴纸分类：天气、交通、美食、景点、心情、酒店、购物和演唱会。
- 贴纸可以放在封面页、每日页、照片区、时间轴节点或备注区。
- MVP 支持简单移动、缩放、旋转和删除。
- MVP 不包含高级图层管理、混合模式、对齐工具、自定义贴纸上传或贴纸市场。

模板：

- MVP 从 1-2 个简单模板开始。
- 推荐首批模板：
  - 简约手帐。
  - 旅行计划卡片。
- 后续版本可以增加胶片、复古、拼贴、杂志、可爱和高级付费模板包。

## 分享与导出

分享属于 MVP，因为它有助于产品传播。

MVP 导出格式：

- 适合社交平台分享的长图。
- 适合快速发布的计划卡片图。
- 适合保存或发给同行人的 PDF。
- 适合导入其他 AI 工具、Notion、Obsidian、Apple Notes 或手动编辑的 Markdown。

Markdown 导出应包含：

- 旅行标题。
- 日期。
- 目的地。
- 旅行目的。
- 每日行程。
- 地点备注。
- 手帐记录。
- 预算摘要。
- AA 结算摘要。
- 行李清单。

MVP 分享内容应包含轻量品牌露出或水印，但不能破坏视觉质量。

AI SNS 文案：

- 导出分享时，AI 可以生成适合小红书或其他 SNS 平台发布的标题、正文和标签。
- 文案应基于真实行程内容生成，避免夸大。
- 默认包含品牌传播标签，例如 `#织步记`，必要时也可加入 `#AyuWalk`。
- 用户可以编辑文案后再复制或分享。

后续分享能力：

- 只读在线分享链接。
- 协作旅行页面。
- 公开旅行手帐页面。
- 基于模板的社交分享卡片。

## 预算、花费与 AA 计算器

预算规划属于出行前规划。

MVP 预算功能：

- 总预算。
- 分类预算，例如交通、酒店、餐饮、门票、购物、娱乐和其他。
- 活动预计花费。
- 在旅行总览中显示预算摘要。

AA 计算器：

- 添加旅行参与人。
- 添加花费项目。
- 记录付款人。
- 选择参与该笔花费的人。
- 自动计算谁应该付给谁。
- 将结算摘要导出到手帐、PDF 和 Markdown。

MVP 可以先聚焦简单均分规则。非均分、汇率转换、票据识别和高级结算优化后续再做。

## 行李清单

行李清单属于出行前规划。

MVP 行为：

- 根据目的地、时长、天气假设、旅行类型和同行人生成默认行李清单。
- 用户可以添加、编辑、删除和勾选物品。
- 物品可以按分类分组。
- 打包进度可以出现在旅行总览和手帐导出中。

后续能力：

- 根据天气智能推荐行李。
- 家庭/同行人共享行李清单。
- 可复用模板。
- 智能提醒。

## 提醒与出行倒计时

提醒能力属于后续增强，但应在模型中预留。

后续提醒包括：

- 出行倒计时提醒。
- 弹窗提醒。
- 锁定界面或系统小组件中的出行倒计时。
- 餐厅预约提醒。
- 关键票务、酒店入住、交通出发提醒。
- 如果目的地当地处于假期、旺季或大型活动期间，在行程规划时提示用户。

MVP 不一定实现完整提醒系统，但 `Trip`、`Activity` 和 `Place` 应预留提醒字段和重要时间字段。

## 技术栈

推荐 MVP 技术栈：

- iOS 原生 App。
- Swift。
- SwiftUI。
- SwiftData 做本地持久化；如果模型迁移或查询复杂度风险较高，可退回 Core Data。
- MapKit 做地图。
- MiniMax 多模态 API 做截图和图片理解。
- 文本模型 API 做行程生成、问答和行程优化。
- 使用 SwiftUI 渲染导出组件，用于图片和 PDF 输出。
- 从结构化旅行与手帐数据生成 Markdown。
- 前期视觉设计环节使用 taste-skill 做审美校准，尤其用于视觉语言、分享卡片、手帐模板和营销展示的设计检查。

后端策略：

- 不先做完整后端。
- 先构建本地优先的数据和真实端到端 App 流程。
- 在任何后端工作前，先定义稳定的数据协议。
- 本地 MVP 稳定后再加入 CloudKit/iCloud 同步。
- 只有在需要订阅、AI 额度、在线分享、协作或跨平台扩展时，再加入自建账号/后端。

这样可以避免之前“后端和前端分开做，最后对不上”的问题。

## 架构

App 应使用清晰的服务边界。

核心层：

- Data Model：管理旅行、行程、预算、花费、行李、手帐、导出和未来协作记录。
- Local Store：在设备本地持久化数据。
- SyncProvider：为 iCloud 和未来后端同步预留接口。
- AIService：封装文本生成、多模态识别、行程优化和结构化 JSON 校验。
- MapProvider：抽象地图操作；MVP 使用 MapKit 实现。
- PlanningEngine：把用户输入、导入资料、AI 输出、地点、时间约束和预算约束转换成可编辑计划。
- PlanningScriptEngine：记录和执行可复用的路径规划脚本、规则和启发式逻辑，用于减少后期重复 AI 调用。
- JournalEngine：把旅行数据转换成手帐页面和模块。
- ExportService：生成图片、PDF 和 Markdown 输出。
- EntitlementProvider：为未来订阅、AI 点数、付费模板和贴纸包预留接口。

MVP 的 UI 可以简单，但这些边界应该尽早存在。

## 核心数据模型

初始实体：

- Trip：一次旅行计划。
- TripDay：旅行中的某一天。
- Activity：一个行程项目，例如景点、用餐、酒店、交通、购物、演唱会、自由时间或备注。
- Place：地点、坐标、地址和地图服务 provider ID。
- ImportedSource：截图、文本或未来链接输入。
- BudgetPlan：按分类和旅行记录预计花费。
- Expense：实际或计划花费项目。
- Participant：旅行参与人，用于 AA 和未来协作。
- PackingList：行李清单分组。
- PackingItem：一个清单物品。
- JournalPage：封面、总览、每日页或总结页。
- JournalBlock：手帐页里的模块化内容块。
- StickerAsset：内置贴纸资源。
- StickerPlacement：贴纸在手帐页或模块中的位置和变换信息。
- ShareExport：图片、PDF 或 Markdown 导出记录。
- Reminder：出行倒计时、预约、交通、入住、活动开始等提醒记录。
- PlanningScript：AI 生成或系统沉淀的可复用规划步骤、排序规则和检查逻辑。

未来预留字段：

- ownerId。
- participants。
- visibility。
- syncStatus。
- cloudRecordId。
- createdDeviceId。
- permissions。
- changeLog。

## AI 设计

AI 功能必须返回结构化数据。

MVP AI 任务：

- 当用户输入过于模糊时，提出补充问题。
- 根据手动输入生成初版行程。
- 通过 MiniMax 多模态 API 从截图中提取结构化旅行信息。
- 从粘贴文本中提取结构化旅行信息。
- 建议路线和时间调整。
- 生成行李清单建议。
- 根据行程数据生成手帐草稿。
- 为小红书或其他 SNS 平台生成可编辑分享文案和标签。

AI 输出应包含假设和不确定性标记，让 UI 可以展示提醒，而不是把猜测内容静默当成事实。

路径规划应采用 AI 与脚本并行的模式：

- AI 负责理解用户意图、处理模糊信息、生成初始路线和解释调整原因。
- 脚本负责可重复的确定性检查，例如路线顺序、时间冲突、饭点空档、预算分类、提醒触发和编号标注。
- 每次 AI 路径规划的输入、输出、假设、调整理由和可复用规则都应记录下来，逐步沉淀成 PlanningScript。
- 后期优先用脚本处理稳定逻辑，只在需要理解、生成、权衡或解释时调用 AI，以减少 AI 调用成本和不稳定性。

## 地图策略

MVP 使用 Apple MapKit，因为它适合 iOS，没有额外地图 SDK 依赖，也适合 Apple 生态用户。

设计上保留 MapProvider 接口，以便后续需要时评估 Mapbox 或 Google Maps。

MapKit 适合：

- 原生 iOS 地图体验。
- 显示旅行地点。
- 自定义标注。
- 路线覆盖层。
- 地图快照。
- App 层视觉设计。
- 编号路线点，例如 1、2、3、4、5。

MapKit 对深度自定义地图底图风格有限。如果产品后续需要完整自定义道路、水域、标签和品牌地图风格，应评估 Mapbox。

## 视觉方向

MVP 视觉风格：

- 简约手帐风。
- 清晰、克制、轻量。
- 适合实际规划。
- 有柔和的手帐感，但不要让规划流程变得装饰过重或低效。

规划工作台应该清晰高效。手帐输出可以通过模板、贴纸、封面页和导出卡片承载更多个性。

设计流程：

- 前期设计环节使用 taste-skill 做视觉审美校准。
- 由于 taste-skill 更偏视觉和前端审美，不直接替代 iOS 产品交互设计。
- 对织步记/Ayu Walk 的使用重点应放在：简约手帐风、分享卡片、手帐模板、页面层级、排版、留白、动效克制和避免模板化视觉。

## 商业化预留

MVP 不需要自建账号系统。

未来付费功能可以包括：

- 更多 AI 规划额度。
- 高级行程优化。
- 高级手帐模板。
- 高级贴纸包。
- 高清导出。
- 更多旅行计划。
- 协作功能。
- 在线分享页。
- 高级提醒小组件和锁定界面倒计时样式。

iOS 商业化优先使用 Apple In-App Purchase，除非跨平台账号能力变成必要。

## 风险与应对

风险：MVP 范围过大。
应对：先做端到端薄切片：创建旅行、生成行程、编辑时间轴、生成手帐、导出 Markdown/图片。

风险：AI 返回不可用的自然语言。
应对：要求 AI 响应符合 JSON schema，并做校验。

风险：前端和后端脱节。
应对：本地优先 MVP、共享数据协议、后端实现前先用 mock JSON、按端到端小闭环推进。

风险：手帐编辑器变得太复杂。
应对：模块化轻编辑、有限模板、有限贴纸控制，MVP 不做自由画布编辑器。

风险：AI 路径规划成本过高。
应对：记录 AI 规划路径并沉淀成可复用 PlanningScript，在调用 AI 前优先运行确定性脚本。

风险：MapKit 风格能力不足。
应对：保留 MapProvider 抽象，先把自定义视觉放在标注、路线、卡片、手帐模板和导出布局里。

风险：社交平台链接导入不稳定。
应对：MVP 先支持截图和粘贴文本，链接解析作为未来能力。

## 建议 MVP 构建顺序

1. 定义数据模型和示例旅行 JSON。
2. 构建本地旅行创建流程。
3. 构建 AI 文本行程生成，要求结构化输出。
4. 构建截图/文本导入流程，接入 MiniMax 多模态 API。
5. 构建行程时间轴编辑器。
6. 构建 MapKit 地点显示、路线连线、编号标注和基础拖动/重排行为。
7. 构建预算规划。
8. 构建 AA 计算器。
9. 构建行李清单。
10. 构建 AI+脚本并行的规划记录与可复用规则机制。
11. 构建手帐生成引擎。
12. 构建翻页式手帐预览。
13. 构建带贴纸和模块选择的模块化手帐编辑器。
14. 构建图片、PDF 和 Markdown 导出。
15. 加入轻量分享品牌露出和 AI SNS 文案生成。
16. 准备提醒、iCloud/同步/账号接口，但不实现完整后端。

## 实施前默认假设

- 英文产品名为 Ayu Walk。
- 最低 iOS 版本应在实施规划阶段确定，届时需要检查 MapKit、SwiftData、导出和照片能力需求。
- SwiftData 是默认持久化选择，除非原型验证发现迁移、查询或同步风险足以需要 Core Data。
- 文本模型 provider 在实施规划阶段选择；接口不能绑定死某一个 provider。
- MiniMax API 请求和响应 schema 应在实现截图导入前确认。
- MVP 目标包含 Markdown 和图片导出；PDF 属于产品范围，但如果需要，可以排在首个端到端薄切片之后。
- 在线只读分享链接属于 MVP 后续能力，除非主动把账号和云基础设施提前。
